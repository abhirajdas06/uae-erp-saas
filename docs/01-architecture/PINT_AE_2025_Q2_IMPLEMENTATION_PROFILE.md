## 1. Purpose and Limits

This document records the structure of the OpenPeppol UAE `2025-Q2` technical publication and defines how the ERP should consume a specifically approved PINT AE release. It is not a legal-applicability decision, provider accreditation, conformance certificate or approval to enable self-billing or production submission.

The publication landing page displays release date 9 June 2025. Billing and Self-Billing release notes identify version `1.0.0`, release date 10 June 2025, and last update 9 June 2025 UTC. Preserve those published facts rather than silently choosing one date. The path `2025-Q2`, artefact checksums and release-note version jointly identify this candidate baseline; a qualified reviewer must confirm the currently operative/contracted version before implementation.

## 2. Published Document Families

| Family | Transactions | Initial ERP posture |
|---|---|---|
| PINT AE Billing | Invoice; Credit Note | Candidate P04 scope after applicability/rules approval |
| PINT AE Self-Billing | Self-Billed Invoice; Self-Billed Credit Note | Disabled until self-billing business, tax, contractual and provider scope is separately approved |

The publication states that Self-Billing uses the same data model as PINT AE Billing. This does not make actor roles, authority, issuance, numbering, correction or provider workflows interchangeable; those remain explicit transaction-profile rules.

## 3. Artefact Structure

Each transaction exposes a coordinated artefact set:

1. Semantic model: business groups (`IBG-*`), business terms (`IBT-*`), UAE-distinct terms (`BTAE-*`), definitions, section classification and cardinality.
2. Syntax binding: mapping from semantic terms/cardinality into UBL XML elements/attributes and qualifiers.
3. Code lists: allowed external and UAE-specific values.
4. Business rules: semantic, conditional, arithmetic, cardinality and code-list constraints with rule identifiers.
5. Schematrons: executable shared PINT and AE-specific validation artefacts.
6. Release notes and downloadable resource archive: exact version/inventory required for build/test evidence.

The semantic classification is material:

- `Shared`: common PINT term.
- `Aligned`: term aligned through the PINT methodology.
- `Distinct`: UAE-specific extension, commonly represented by `BTAE-*` identifiers.

Do not infer implementation priority from these labels. Cardinality, applicable transaction profile, code list and business rules determine whether a term is required.

## 4. UBL Envelope and Core Structure

The Invoice syntax binding uses `ubl:Invoice`. Important control fields include:

- `cbc:CustomizationID` for specification identifier (`IBT-024`).
- `cbc:ProfileID` for business process type (`IBT-023`).
- `cbc:ProfileExecutionID` for UAE transaction type (`BTAE-02`).
- `cbc:ID` for invoice number (`IBT-001`).
- `cbc:UUID` for the globally unique identifier (`BTAE-07`).
- `cbc:IssueDate`, optional issue time, type code and document/tax currency.

Major semantic groups cover process control; preceding invoice references; seller, buyer, payee and tax representative; addresses and delivery; invoice period; payment instructions; document/line allowances and charges; tax breakdown/totals; monetary totals; invoice lines; item/price/classification; and supporting documents. Credit-note and self-billing bindings must be taken from their own exact transaction artefacts, not generated by renaming invoice elements.

Electronic endpoint identifiers and their schemes are explicit. Seller and buyer legal/tax identifiers, issuing authorities, UAE transaction flags, tax categories and other UAE-distinct terms require exact approved mapping; missing values are validation findings and must never be fabricated.

## 5. Code-List Governance

The 2025-Q2 Billing Invoice publication lists, among others:

- `AETaxCat` UAE VAT categories.
- `AE-TransType`, an eight-position binary flag string whose positions have defined meanings.
- `AE-Exempt`, `AE-FreqBill`, `AE-ItemType` and `AE-GoodsType`.
- ISO 3166-1 country and ISO 4217 currency codes.
- Electronic Address Scheme (`EAS`) and ISO 6523 ICD identifiers.
- UNTDID document, allowance/charge, object/item and payment-means subsets.
- UNECE unit codes and the PINT media-type subset.

Code lists are release artefacts, not application enums copied once. Store list identifier, release/profile, retrieved checksum, effective use, source and mapping version. Unknown or retired values fail validation or enter an explicit migration/review path; they are never silently coerced.

## 6. Layered Validation Strategy

Validation is deterministic and version-pinned:

1. Source-domain validation: issued invoice/credit note is immutable, internally balanced and eligible.
2. Applicability/profile selection: approved transaction family, effective ruleset, tenant/legal entity and provider capability.
3. Mapping validation: every internal snapshot field maps to a semantic term or documented exclusion.
4. UBL structural validation: exact root, namespaces, element/attribute types and syntax cardinality from the approved resources.
5. Shared PINT Schematron rules.
6. AE-specific Schematron rules for the applicable UAE sender/receiver capability.
7. Code-list validation against the pinned release.
8. Provider-contract preflight without weakening or rewriting PINT AE findings.
9. Cross-field financial reconciliation with the immutable invoice/VAT snapshot.

The publication distinguishes shared PINT rules from AE-specific rules. Store validation layer, rule ID, severity, source version and safe message. Do not flatten all failures into a provider rejection or infer regulatory acceptance from local validation success.

## 7. Canonical Mapping Register

The ERP canonical snapshot remains provider-neutral and source-derived. PINT AE XML is a versioned external representation, not the Accounting or Invoicing aggregate.

For every supported term, maintain a reviewable mapping row containing:

| Field | Required content |
|---|---|
| Internal source | Immutable snapshot path and owner |
| Semantic target | `IBG`/`IBT`/`BTAE` identifier and definition |
| Syntax target | Exact UBL element/attribute path and qualifier |
| Applicability | Billing/Self-Billing; Invoice/Credit Note; condition and cardinality |
| Transformation | Normalization only; no invented business/tax fact |
| Code list | Identifier and pinned release/checksum |
| Precision | Source precision, serialization and approved rounding stage |
| Sensitivity | Classification, logging/file/export restrictions |
| Verification | Golden fixture, rule IDs, negative/boundary tests and reviewer |

Mapping output records profile/version, mapping version, Schematron/resource checksums, source snapshot hash and serialized payload hash. Reprocessing an old document uses its historical versions unless a separately authorized migration/resubmission rule applies.

## 8. Amount, Tax and Attachment Strategy

PINT AE validation consumes approved invoice/VAT facts; it does not define the ERP’s accounting policy. Decimal calculation and rounding occur under ADR-013 and the approved P03/P05 policy, then reconcile to document/line/tax/monetary totals required by the profile. The publication contains rules limiting several document-level monetary values to two decimals; exact rules from the pinned release are executable validation inputs, not a universal database-scale decision.

Supporting documents use the exact semantic/syntax and media-code rules. Files remain governed by ADR-019: private storage, authorization, size/type/content scanning, checksum/version, approved retention and safe provider transfer. Never embed an attachment merely because the source file exists.

## 9. Version and Change Strategy

- Archive the complete resource package without editing it; record retrieval time, source URL, file inventory and SHA-256 digests.
- Treat Billing, Credit Note, Self-Billing and Self-Billing Credit Note as separate contract profiles even where their data model overlaps.
- Keep semantic mapping, syntax serialization, code-list bundle, business rules, Schematron runner and provider adapter independently versioned but compatibility-tested as a release set.
- Compare new releases by term/cardinality, syntax path, code list, rule, identifier and example changes; classify breaking/data/migration/provider impacts.
- Run old and new validators against golden/negative historical fixtures before approval. Do not silently revalidate or rewrite submitted historical payloads.
- Production cutover names the profile/resource/mapping/provider versions, supported document types, effective date, rollback/disable path and reviewer.

## 10. Required Test Evidence

- Resource archive inventory/digests and repeatable offline validation command.
- One positive and negative fixture per approved transaction/profile, including minimum/maximum cardinalities and UAE-distinct terms.
- Semantic-to-UBL mapping coverage with no unmapped mandatory/conditional term.
- Shared PINT, AE-specific, code-list, arithmetic/rounding and provider-preflight failures reported distinctly.
- Golden serialization, canonicalization/hash stability where defined internally, namespace/encoding and unsafe-content tests.
- Invoice/credit relationship, tax-currency/AED-total, transaction-type, endpoint/identifier, allowance/charge, payment and attachment cases applicable to approved scope.
- Historical version coexistence, change/diff, migration/cutover, provider sandbox/conformance and recovery evidence.

No test pass constitutes legal applicability, ASP accreditation, production acceptance or UAE compliance.
